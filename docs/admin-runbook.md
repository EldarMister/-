Доработка от 28 октября 2026: [интерфейс по шаблону, пять языков, история уведомлений, восстановление realtime и новые проверки](admin-revision-2026-10-28.md). Текущий admin service worker — v6; сведения о старых прогонах ниже сохранены как история проверки.

Изменения находятся в ветке `codex/admin-template-rebuild`. Production не публиковался. Данные и секреты существующего окружения сохраняются; новые проверки выполнялись с отдельной тестовой PostgreSQL. Таблица переноса и ограничения: [admin-feature-parity.md](admin-feature-parity.md). Источник шаблона и MIT-лицензия: [admin-template-source.md](admin-template-source.md).

## Обычный локальный запуск

Требуются Node.js 22.13+ и PostgreSQL. Настройте `.env` по `.env.example`, указывая предназначенную для разработки базу. Существующий `.env` не следует перезаписывать.

```powershell
npm install
npm run db:migrate
npm run dev:full
```

По умолчанию витрина работает на `http://localhost:3000/catalog/1`, панель — `http://localhost:3000/admin/`, API — `http://localhost:4000/api`. PWA использует точку запуска `/admin/app`, входящую в scope `/admin/`; этот маршрут проверен в браузере. Для разделённых локальных портов frontend использует `NEXT_PUBLIC_API_URL`, а API должен разрешать конкретный frontend origin через `CORS_ORIGIN`. В production приложение уже использует общий домен и относительный `/api`.

`db:migrate` применяет схему, но не запускает `db:seed`. Обычная инициализация API в этом проекте исторически заполняет каталог, если база пуста; проверяйте выбранную `DATABASE_URL` перед запуском. Не запускайте `db:seed` против рабочей базы для проверки интерфейса. Для новой тестовой базы используйте только отдельный тестовый экземпляр. Пересоздание и очистка рабочей базы не требуются.

## Вход и права

Существующая первая учётная запись однократно становится OWNER миграцией `2026-10-25-admin-v2-access`. Её текущий пароль сохраняется. `ADMIN_PASSWORD` используется для первоначального создания владельца в пустой базе и больше не перезаписывает пароль при каждом запуске API. В development при создании пустой базы действует существующий резервный пароль `ChangeMe123!`; на существующей базе он ничего не меняет. Для production `JWT_SECRET` должен быть частным значением от 32 символов, а начальный `ADMIN_PASSWORD` — от 12 символов.

Вход владельца сохраняет возможность оставить логин пустым. Другие сотрудники входят по email и паролю. Создание сотрудников и назначение ролей выполняет владелец в разделе «Персонал». Доступ хранится в PostgreSQL, сессии — серверные записи с HttpOnly cookie.

Роли ровно три:

- OWNER имеет все права, его доступ не ограничивается персональными overrides. Последнего активного владельца нельзя заблокировать или понизить.
- ADMIN по умолчанию имеет рабочие права. Создание учётных записей, назначение ролей и управление доступом остаются за владельцем. Администратор не может сбросить пароль владельца или вернуть себе отозванные разрешения.
- MANAGER по умолчанию получает `orders.view`, `orders.status`, `users.view`, `users.edit`. Удаление, массовые операции, экспорт, аналитика и каталог автоматически не выдаются.

Матрица поддерживает наследование от роли, явное разрешение и запрет. После сохранения следующая серверная операция сотрудника проверяет новые права. Интерфейс дополнительно обновляет сессию через события/проверку состояния. Блокировка удаляет сессии и подписки. Разделы и кнопки скрываются по effective permissions, но защита API выполняется независимо от интерфейса.

## Новые совместимые миграции

`server/migrate.ts` выполняет `server/schema.sql`, затем `server/admin-schedules-schema.sql`. Новый код не удаляет существующие рабочие таблицы или историю заказов.

| Изменение | Назначение |
|---|---|
| `admin_users.role`, `active`, `permission_overrides` и ограничение трёх ролей | Роли, блокировка и персональные права |
| Однократная запись `2026-10-25-admin-v2-access` | Повышение исходной учётной записи до владельца и дата начала учёта |
| `admin_audit_log` и индекс времени | Важные действия без паролей/токенов |
| `order_status_history` и индексы | Автор и время перехода статуса |
| `order_items.category_id_snapshot`, `category_name_snapshot` nullable | Категория новых заказов без изменения старой истории |
| `admin_push_subscriptions`, `session_token_hash` | Привязка устройства к сотруднику и сессии |
| `admin_push_deliveries` | Защита от повторной серверной отправки одного заказа |
| `admin_order_created` и изменения триггеров | Уведомление PostgreSQL после успешной фиксации заказа, обновления прав |
| Индексы заказов по телефону/дате и точке/дате | Серверные списки и аналитика |
| `location_schedules` в отдельном SQL-файле | Недельные интервалы, версия и автор изменений |

Старые поля `hours`, `opens_at`, существующие slug, идентификаторы и снимки позиций заказов сохраняются. Категории старых заказов не заполняются по текущему каталогу. Старая история действий сотрудников не создаётся.

Сами SQL-файлы содержат и прежние миграции проекта. Перед рабочим применением проверьте состояние `app_migrations` и резервную копию обычным порядком эксплуатации. В этой работе миграции запускались на тестовых базах, не на production.

## Расписание и оформление заказов

В разделе «Время работы» задаются дни недели и интервалы, включая перерывы и переход через полночь. Часовой пояс — `Asia/Bishkek`. У старых точек ограничение изначально выключено. Чтобы оно начало влиять на новые заказы, сотрудник с `schedules.edit` должен явно включить «Принимать заказы только в рабочие интервалы». Вне рабочего времени публичный `POST /api/orders` возвращает 409. Старые заказы не меняются. Настройки сохраняются с номером версии, поэтому параллельное устаревшее изменение не перезаписывает актуальное.

Текст часов в карточке точки и новый недельный график следует согласовать вручную. Календарные исключения в исходном проекте отсутствовали и не добавлены. Подробные правила и способ отключить ограничение: [admin-schedules.md](admin-schedules.md).

При смене статуса заказа клиент отправляет `{ status, expectedStatus }`. Если заказ уже перешёл в целевой статус, повтор считается успешным без повторного начисления наград. Если сотрудник действует по другому устаревшему статусу, сервер возвращает 409 и предлагает обновить карточку. Интеграции, вызывающие этот административный метод напрямую, должны передавать прочитанный статус.

## Звук, PWA и Web Push

В профиле сотрудника доступны включение/выключение звука, проверка и громкость. Настройки сохраняются отдельно для сотрудника и браузера. AudioContext активируется явным действием. Событие имеет стабильный идентификатор `order:<id>`; Web Locks и локальный ledger координируют вкладки, а при отсутствии Web Locks атомарное получение события выполняется через IndexedDB. Недоступность хранилища означает пропуск звука, а не воспроизведение сразу во всех вкладках. Начальная загрузка, изменение фильтра и синхронизация после reconnect не считаются новыми событиями. Отдельный системный Web Push включается своей кнопкой и разрешением браузера.

PWA manifest и service worker ограничены `/admin/`. Кэшируются общедоступная страница отсутствия соединения, иконки, логотип, локальные шрифты и подходящие статические JS/CSS-файлы с хешем версии; кэш ресурсов ограничен 60 записями. Проверяются тип ответа и запреты `private/no-store`, `Vary: Cookie/Authorization` и `Set-Cookie`. Заказы, персональные данные, отчёты, авторизованные API и персонализированный HTML не кладутся в постоянный offline-кэш. В offline нельзя сохранить заказ «успешно» или поставить критичное действие в скрытую очередь. При обновлении показывается предложение, перезагрузка требует действия пользователя. При выходе очищается пользовательское состояние, старые приватные административные кэши и серверная привязка push этого устройства; явно публичные ресурсы остаются, чтобы работала offline-инструкция.

Для production требуется HTTPS на общем домене сайта/API. На локальном `localhost` браузеры допускают работу service worker без внешнего сертификата. Установка зависит от браузера: Chrome/Edge могут показать собственный prompt, iPhone/iPad используют Safari → Поделиться → На экран «Домой». Это не гарантирует постоянное соединение или доставку при закрытом приложении.

Для серверной отправки Web Push добавьте секретные переменные только в серверное окружение:

```dotenv
VAPID_PUBLIC_KEY=<публичный VAPID-ключ>
VAPID_PRIVATE_KEY=<секретный VAPID-ключ>
VAPID_SUBJECT=mailto:your-support@example.com
```

Пару ключей можно создать установленным `web-push`:

```powershell
node --input-type=module -e "import webpush from 'web-push'; console.log(webpush.generateVAPIDKeys())"
```

Не добавляйте ключи в Git и не используйте префикс `NEXT_PUBLIC_` для секретного ключа. Публичный ключ выдаётся разрешённому клиенту через `/api/admin/push/public-key`. Отсутствие VAPID явно показывается в профиле; звук открытой панели работает отдельно. Получатели отбираются по действующим правам и активности. Системное уведомление не содержит имени, телефона, адреса или суммы клиента. Открытие заказа снова проходит авторизацию.

Production HTTPS, реальные VAPID-ключи и внешняя доставка Web Push в этой работе не настраивались и не подтверждались.

## Проверки и отдельная тестовая база

Основные команды:

```powershell
npm run typecheck
npm run lint
npm run build
npm run test:admin
```

Подтверждён финальный полный `npm test`: типы, production-сборка, 35 MJS-тестов (26 пройдено, 9 интеграций пропущены без подключения), 65 существующих TS-тестов и 20 административных тестов, включая IndexedDB-дедупликацию. Двенадцать VM-тестов service worker проверяют кэш/offline/update/push; они не означают установку приложения в ОС.

Отдельно с настоящей тестовой PostgreSQL успешно выполнены все 9 API-интеграций: безопасность, SSE-авторизация, live events, расписание, аналитика, прежние награды, точки, удаление с повторной инициализацией/перезапуском и CRUD/настройки/загрузки. В аналитику входят вручную рассчитанные суммы, исключение отмен, дата в Бишкеке, история каталога, сравнение CSV, права менеджера и отзыв доступа. Старый тест наград обновлён для передачи `expectedStatus` и также пройден.

Финальный полный lint не выявил ошибок; остались 17 предупреждений об `<img>`. Это не нулевое количество предупреждений всего проекта.

Тест безопасности `tests/admin-security-api.integration.test.mjs` создаёт сотрудников и заказы. Он должен работать только с API на отдельной тестовой базе. Для него указываются `ADMIN_API_INTEGRATION_URL` и пароль тестового владельца `ADMIN_PASSWORD`; не направляйте его на рабочий сайт.

Тест аналитики сам создаёт временную базу с префиксом `sushi_admin_test_analytics_`, запускает API на свободном порту и после теста удаляет только эту базу. Контрольная база должна быть локальной и иметь префикс `sushi_admin_test_` или `daana_admin_test_`. Нужны права PostgreSQL на создание баз:

```powershell
$env:ADMIN_ANALYTICS_TEST_DATABASE_URL='postgres://test_user@127.0.0.1:5544/daana_admin_test_local'
node --test tests/admin-analytics-api.integration.test.mjs
```

Порт 5544 — пример отдельного тестового PostgreSQL, не обязательный порт приложения. В фактическом прогоне использовались изолированный PostgreSQL на 5544, тестовый API на 4100 и отдельный браузерный frontend на 4180. Не переносите тестовые данные и учётные записи в production.

Отсутствие переменной окружения у интеграционного теста приводит к пропуску, а не к подтверждению сценария. Поэтому выше отдельно указаны обычный `npm test` и фактический прогон подключённых API-интеграций.

В браузере открыты основные рабочие экраны при 1440, светлая/тёмная темы; редактор товара при 390 и предупреждение несохранённых изменений; заказы при 360/768 без горизонтального переполнения всей страницы. Новый заказ показал toast поверх открытого каталога. Кнопка проверки активировала AudioContext и DOM-статус звука. Менеджер попал в заказы с ограниченным меню, прямой URL персонала показал «Нет доступа». Отзыв заказов/пользователей и выдача наград владельцем обновили доступ менеджера без перевхода; реальные данные наград успешно загрузились независимо от доступа к клиентам.

Проверены загрузка `/admin/app` и настоящее обновление service worker v2→v3 во встроенном браузере: баннер, предупреждение, явное «Обновить сейчас», перезагрузка с сохранением сессии и исчезновение баннера. Снимки и точный перечень находятся в [admin-feature-parity.md](admin-feature-parity.md#сохранённые-изображения).

Нативная установка PWA в ОС, физический звук и одновременная работа реальных вкладок не проверялись. Автотесты этих механизмов не подменяют проверку конкретного браузера/ОС. Системный Web Push не настроен без VAPID; реальная доставка, production HTTPS, реальные SMS, Яндекс API и блокчейн-переводы не выполнялись.

Offline fallback также проверен в настоящем встроенном браузере: после явного обновления до worker v4 тестовый web-сервер 4180 остановлен, перезагрузка `/admin/app` показала «Нет соединения» из публичного кэша без заказов и контактов. Кнопка восстановления ведёт в `/admin/app`; web-сервер затем запущен снова. Это имитация недоступности сети/сервера, а не отключение сетевого адаптера ОС.

## Переключение и откат

До отдельного разрешения владельца эту ветку не публиковать в production. На тестовом окружении используйте копию данных без производственных токенов и отдельные ключи внешних сервисов.

Добавленные столбцы и таблицы совместимы со старыми данными; для возврата интерфейса не требуется удалять их или восстанавливать базу «с нуля». Перед переключением зафиксируйте версию приложения, резервную копию БД и текущие переменные окружения. Для отключения нового влияния графика на checkout выключите ограничения недельного расписания.

Предпочтительный откат интерфейса сохраняет новый сервер с проверками прав. Полный возврат прежнего сервера также вернёт прежнюю модель безопасности, в которой нет персональных ограничений: это нужно учитывать при планировании отката и доступности `/admin`. Не удаляйте новые данные аудита, снимки категорий и историю статусов ради отката. Публичные API и прежние сущности сохранены; новые методы и `expectedStatus` должны быть согласованы с версией административного клиента. Перед возобновлением работы после отката проверьте вход, доступы, создание заказа и начисление наград на тестовом окружении.

Дополнительная проверка приватности: право `users.view` без `orders.view` позволяет работать с контактами, но API не возвращает количество покупок, выручку, дату последнего заказа или историю заказов. Вложенный запрос истории возвращает 403. Интерфейс не запрашивает эту историю и очищает ранее открытые данные при отзыве прав. Корректировка наград требует `loyalty.adjust` и `users.view`; персональная матрица показывает зависимость. Сценарии проверены на новой изолированной фикстуре.

Дополнительный интеграционный прогон паритета проверил создание категории без slug, сохранение slug при переименовании, товар/цену/категорию/архив и неизменность старого заказа, полный CRUD акций, сохранение и валидацию общих настроек. Загрузка PNG проверена по настоящим байтам: исходное имя `.html` не определяет расширение, поддельный HTML отклонён с 400, превышение 5 МБ — с 413. Настройки тестовой базы восстановлены, тестовый загруженный файл удалён.

Итоговый повторный `npm test` на окончательном коде прошёл: TypeScript, production build, 35 MJS-тестов (26 пройдено, 9 интеграционных пропущены без подключения), 65 прежних TS-тестов и 20 admin-тестов. Все 9 подключённых API-интеграций выполнялись отдельно на изолированных базах. Итоговый lint — 0 ошибок и 17 предупреждений оптимизации `<img>`. Серверная проверка состояния push-подписки также проверена: привязка только текущему сотруднику, запреты 401/403, отзыв и повторная выдача прав не создают ложного состояния включённых уведомлений.
