# Аналитика административной панели

Отчёт строится сервером из PostgreSQL. Интерфейс и CSV используют одну функцию `loadAnalytics`, одну схему фильтров и одинаковые формулы. В пределах одного ответа все выборки выполняются в read-only транзакции `REPEATABLE READ`. Экспорт, сделанный позже, отражает состояние базы на момент экспорта: если сотрудники изменили заказы между запросами, цифры могут измениться.

## Период и фильтры

`GET /api/admin/analytics?from=2026-10-01&to=2026-10-25&locationId=4`. Даты включительны в часовом поясе `Asia/Bishkek` (UTC+6). В SQL используются полуоткрытые границы `[начало первого дня; начало следующего дня после последнего)`. Период — от 1 до 366 дней. По умолчанию последние 30 календарных дней. Предыдущий период содержит ровно столько же дней и заканчивается перед выбранным.

Исходная модель содержит точки самовывоза, а отдельной сущности города в ней нет. Фильтр — по фактической точке заказа (`orders.location_id`), включая исторические неактивные точки. Фиктивное разделение по городам не вводилось. Аналитика датируется временем **создания заказа**, а статус оценивается на момент расчёта. Это означает, что завершённый сегодня заказ, оформленный вчера, относится ко вчерашней выручке. Учёта бухгалтерских дат платежей нет.

## Формулы

| Показатель | Формула |
|---|---|
| Всего заказов | Количество заказов всех шести существующих статусов по дате оформления |
| Выдано | Количество со статусом `completed` |
| Отменено | Количество со статусом `cancelled` |
| В работе | Количество со статусом `new`, `confirmed`, `preparing`, `ready` |
| Выручка | Сумма сохранённого `orders.total` только для `completed` |
| Средний чек | Выручка / количество `completed`; при отсутствии выданных заказов 0 |
| Изменение | `(текущий − предыдущий) / предыдущий × 100%`; оба 0 → 0%; предыдущий 0, текущий >0 → «Нет базы для сравнения» |
| Дни и часы | Количество всех заказов и выручка выданных, сгруппированные по дате/часу оформления в Бишкеке |
| Популярные товары | 20 названий с наибольшей суммой `order_items.quantity` в выданных заказах; выручка — сумма сохранённых `line_total` |
| Категории | Те же суммы по `category_name_snapshot`, записанному при оформлении новых заказов |
| Новые клиенты | Уникальные телефоны в выбранном периоде, чей первый заказ за всю доступную историю создан в этом периоде |
| Повторные клиенты | Уникальные телефоны в выбранном периоде, чей первый заказ создан раньше начала периода |
| Действия сотрудников | Количество записей `order_status_history` по сотруднику и фактическому времени перехода статуса; отдельно переходы в `completed` и `cancelled` |

Отменённые заказы включены в количество заказов и определение первого обращения клиента, исключены из выручки, среднего чека и продаж товаров. Доставка, скидки, платежи и возвраты отдельно не учтены исходной схемой; эти суммы не прибавляются и не вычитаются искусственно. Выручка не называется прибылью: данных себестоимости нет. Валюта сохранена — кыргызский сом (`С`).

Название товара и его цена берутся из снимка позиции заказа, а не текущего каталога. Для категорий добавлен nullable снимок при новых заказах. Старые записи без достоверного снимка показываются как «Категория не записана», без восстановления вымышленной истории. Одинаковые сохранённые названия товаров агрегируются вместе; переименование товара в новых заказах создаёт отдельную строку.

Список дней и часов содержит нулевые значения для пустых интервалов. Отсутствие моделей модификаторов, комплектаций и возвратов обозначается отдельно как «Данные не собирались». Для сотрудников добавлен журнал действий на будущее; прошлые KPI обработки не восстанавливаются. Дата начала журнала берётся из `app_migrations.applied_at` миграции новой панели. Действия агрегируются по моменту изменения статуса, а не дате оформления заказа, что явно указано в карточке. Это не выручка сотрудника и не число назначенных ему заказов. Дата самого раннего заказа отображается из реальной базы, фиксированной даты начала истории нет.

## Права и экспорт

`analytics.view` защищает чтение отчёта. `analytics.export` — отдельное право выгрузки `/api/admin/analytics/export` с теми же query-параметрами. CSV содержит агрегаты без имён и контактов клиентов. Строковые значения экранируются, потенциальные формулы электронных таблиц нейтрализуются. Ответы имеют `Cache-Control: no-store`.

Проверки `tests/admin-analytics.test.ts` охватывают границы дат, UTC+6, високосный день, сопоставимый период, ограничения диапазона, фильтр точки, нулевую базу сравнения и соответствие агрегатов выгрузке. Это модульные проверки; они не подтверждают SQL против реальной базы без отдельного интеграционного прогона.

`tests/admin-analytics-api.integration.test.mjs` создаёт отдельную временную PostgreSQL-базу и запускает API с ней. Проверяет вручную рассчитанную фикстуру: три заказа текущего периода, один завершённый с выручкой 525 С, один отменённый и один активный; предыдущая выручка 800 С; границы суток; исторические снимки каталога; категории без старого снимка; новых и повторных клиентов; действия сотрудников; совпадение CSV. Также проверяет запрет аналитики и экспорта менеджеру, отсутствие данных наград в разрешённой карточке клиента и отзыв права просмотра клиента без перевхода. Для запуска задайте `ADMIN_ANALYTICS_TEST_DATABASE_URL` на локальную выделенную базу с префиксом `sushi_admin_test_` или `daana_admin_test_` и выполните `node --test tests/admin-analytics-api.integration.test.mjs`. Пользователь тестовой PostgreSQL должен иметь право создания баз. Рабочая база в этом тесте не используется.
