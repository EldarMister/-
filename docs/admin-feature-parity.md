# Соответствие функций административной панели

Последующая доработка 28 октября: [новая композиция шаблона, переводы админки, журнал уведомлений и фактическая проверка realtime/PWA](admin-revision-2026-10-28.md).

Аудит выполнен 25 октября 2026 года по доступным исходникам проекта. Основа — React 19, App Router через vinext, Express, PostgreSQL. Рабочая ветка: `codex/admin-template-rebuild`. Уже существовавшие незакоммиченные изменения сохранены. Production не переключался; рабочая база не пересоздавалась.

Шаблон: [shadcnstore/shadcn-dashboard-landing-template](https://github.com/shadcnstore/shadcn-dashboard-landing-template), Next.js-версия, commit `866423741fa4b62d5e9427603cb2174aedf00f80`. Источник компонентов, лицензия и адаптация описаны в [admin-template-source.md](admin-template-source.md). Выбрана совместимая с текущим App Router версия; сервер и механизм данных сохранены.

Статус «проверено API» означает фактически запущенный автоматический сценарий. «Перенесено; проверено по исходникам» означает, что обработчики и интерфейс присутствуют и проходят сборку/проверку типов, но полный пользовательский сценарий отдельно не подтверждён. Браузерные проверки и скриншоты перечислены в конце отчёта; сборка сама по себе их не подтверждает.

## Данные, которых нет в исходной модели

Отдельных сущностей модификаторов, групп выбора, комплектаций, городов, доставочных зон, тарифов, возвратов и себестоимости в доступном коде и SQL нет. Они не подменялись тестовыми страницами или данными. В модели есть категории, товары и точки самовывоза. Новые интерфейсы не переименовывают точку в «город» и не смешивают комплектации с модификаторами.

Это ограничение полного соответствия исходному заданию: самостоятельное управление модификаторами/комплектациями/городами не реализовано, потому что их бизнес-модель и клиентский выбор отсутствуют в проекте. Для их добавления потребуется отдельная согласованная модель и изменение оформления заказа. Аналитика прямо показывает отсутствие учёта вместо нуля. Возвраты, отдельные платежи, скидки, доставка и прибыль не выдуманы.

Недельное расписание добавлено как новая возможность. Старые `hours` и `opens_at` сохранены. Исключений по календарным датам в прежнем коде нет, новая версия их не реализует. Витрина продолжает показывать прежнее текстовое расписание; его следует согласовать с недельным графиком вручную. Подробнее: [admin-schedules.md](admin-schedules.md).

Исторические категории не восстанавливаются по текущему каталогу: для старых заказов без снимка отображается «Категория не записана». Старые события обработки и персональные KPI не генерируются. Правила расчётов и границы дат: [admin-analytics.md](admin-analytics.md).

## Подтверждённые проверки и оставшиеся проверки

Подтверждён финальный полный прогон `npm test`: `typecheck`, production `build`, MJS-набор из 35 тестов (26 пройдено, 9 интеграций пропущены без переменных подключения), 65 существующих TS-тестов и **20 административных модульных тестов**, включая атомарную дедупликацию через IndexedDB.

Девять интеграционных сценариев **реально выполнены отдельно на тестовой PostgreSQL и API**, без пропусков: административная безопасность, защита SSE-событий, исходные live events, недельное расписание, аналитика, награды, точки, удаление с повторной инициализацией и перезапуском, а также CRUD/настройки/загрузки. Изолированная фикстура аналитики проверяет вручную рассчитанные суммы, границы суток, снимки каталога, CSV, пагинацию истории клиента, редактирование имени, защиту role от mass assignment, отсутствие NFT-данных у менеджера и отзыв доступа без перевхода. Прежний rewards API-тест обновлён для `expectedStatus` и пройден.

Service worker проверен **12 VM-тестами**: область действия, кэширование, offline fallback, безопасное обновление и обработка push. Эти тесты входят в автоматические наборы и не заменяют установку PWA в операционной системе. Финальный полный lint: **0 ошибок, 17 предупреждений** об использовании `<img>`. Предупреждения не объявляются исправленными целиком.

В браузере проверены:

- Desktop 1440: обзор, товары, заказы и подробная карточка заказа, персонал и матрица прав, аналитика, профиль; светлая и тёмная темы.
- Mobile 390: редактор товара и предупреждение о закрытии несохранённой формы.
- Mobile 360 и tablet 768: список заказов; измеренное `scrollWidth` не превышает ширину viewport, горизонтального переполнения всей страницы нет.
- Новый заказ действительно вызвал визуальное уведомление, когда была открыта страница каталога.
- Кнопка проверки звука активировала AudioContext, в интерфейсе показан активный звук. Физическая громкость/воспроизведение не измерялись.
- PWA-точка входа `/admin/app` загружается в scope `/admin/`.
- Менеджер после входа попадает в «Заказы», меню содержит «Заказы», «Пользователи» и «Мой профиль». Прямой URL `?section=staff` показывает «Нет доступа» без списка сотрудников.
- После отзыва владельцем `orders.view`/`users.view` и выдачи `loyalty.view` уже открытая сессия менеджера без перевхода показала отсутствие доступа к старому экрану, обновила меню и успешно загрузила реальные данные наград без доступа к пользователям.
- Настоящее обновление service worker v2→v3 во встроенном браузере прошло через баннер, предупреждающий диалог и явное «Обновить сейчас». Страница `/admin/app` перезагрузилась с сохранённой сессией; баннер исчез.

Не подтверждены нативная установка PWA в ОС, акустическое воспроизведение и несколько одновременно открытых реальных вкладок, production HTTPS, реальная доставка Web Push, реальные SMS, геокодер Яндекса и блокчейн-переводы. Для фонового push VAPID не настроен. Production deployment не выполнялся.

Offline fallback также проверен в настоящем встроенном браузере: после явного обновления до worker v4 тестовый web-сервер 4180 остановлен, перезагрузка `/admin/app` показала «Нет соединения» из публичного кэша без заказов и контактов. Кнопка восстановления ведёт в `/admin/app`; web-сервер затем запущен снова. Это имитация недоступности сети/сервера, а не отключение сетевого адаптера ОС.

Дополнительная проверка приватности: право `users.view` без `orders.view` позволяет работать с контактами, но API не возвращает количество покупок, выручку, дату последнего заказа или историю заказов. Вложенный запрос истории возвращает 403. Интерфейс не запрашивает эту историю и очищает ранее открытые данные при отзыве прав. Корректировка наград требует `loyalty.adjust` и `users.view`; персональная матрица показывает зависимость. Сценарии проверены на новой изолированной фикстуре.

Дополнительный интеграционный прогон паритета проверил создание категории без slug, сохранение slug при переименовании, товар/цену/категорию/архив и неизменность старого заказа, полный CRUD акций, сохранение и валидацию общих настроек. Загрузка PNG проверена по настоящим байтам: исходное имя `.html` не определяет расширение, поддельный HTML отклонён с 400, превышение 5 МБ — с 413. Настройки тестовой базы восстановлены, тестовый загруженный файл удалён.

Итоговый повторный `npm test` на окончательном коде прошёл: TypeScript, production build, 35 MJS-тестов (26 пройдено, 9 интеграционных пропущены без подключения), 65 прежних TS-тестов и 20 admin-тестов. Все 9 подключённых API-интеграций выполнялись отдельно на изолированных базах. Итоговый lint — 0 ошибок и 17 предупреждений оптимизации `<img>`. Серверная проверка состояния push-подписки также проверена: привязка только текущему сотруднику, запреты 401/403, отзыв и повторная выдача прав не создают ложного состояния включённых уведомлений.
